## Findings retained from recent passes

### Input is a request with a stable execution cut

**Owner:** [IN1–IN3](participant-action-system.md#input-history-and-body-interpretation).

The recorder captures input after deterministic interpretation and edge
consumption, while replay injects it before those steps. Reset exposes a
lost cause; portal shaping exposes coordinate-dependent interpretation.
These are consequences of using one mutable representation for admitted
input and its interpreted result.

The bounded correction establishes an immutable admitted value inside
each tick execution, publishes it for all current backend/driver paths,
and records and replays at that same cut. Body interpretation remains
downstream. A physical movement guard resolves the body's frame and
expressible commands before applying a world-space constraint. It must not
change an unrelated attack's aim by rewriting a shared raw axis.

This improves a shared contract for local play, GGRS, hosted input, replay
and harness drivers. It does not require another input manager, general
event log, or wholesale action migration. The smaller qualified-press
coalescing defect is recorded with IN3; it is not the architectural thesis.

### A plan predicts completion; an executor earns it

**Owner:** [LIFE1/LIFE2](radiant-npc-planning.md#dormant-completion--execute-a-supported-prefix-of-the-plan).

Dormant NPC catch-up grants every step's effects after planning. It budgets
each claimed object's hours but not the actor's total sequential work.
It can also grant arrival effects before resolving a destination, and use
current presence to answer a past-hour condition.

The first correction executes only the supported prefix under the existing
schedule clock, books its actual consumed object time, and credits effects
only at completion. Destination and observation assumptions are admitted
explicitly. Hourly cancellation/restart remains a valid policy. A persistent
activity cursor, generic operation catalog and exact hidden physics are not
prerequisites.

This is useful before expanding authored lives or allowing real object use.
It provides a small common execution law for different approximations:
declared preconditions and consumed time constrain which outcomes may be
settled. It does not claim identical live and dormant trajectories.

**Owner:** [SUP1](slopes-feet-ride-surfaces.md#sup1--keep-a-changing-supports-material-motion).
GNU's current hump already meets the support plan's deferred shape-change
customer condition. The producer places its polyline with a similarity,
including scale, then keeps only midpoint displacement and turn. Native
previous-support queries, carry, bounds and point velocity reconstruct a
rigid history. The current mount fixture changes segment length and checks
only its final placement, so it does not prove that history.

The source-phase boundary is separate and necessary. The surface sampler
adds `1/60` to a pinned source coordinate, while GNU's walk advances that
coordinate from distance. Adding configured world `dt` would still guess
another owner's clock. Retain the selected source span and the host's
accepted motion at one declared cut. Source places survive winding and
query order; a reset, disappearance or singular span is not continuous
motion. Preserve the current endpoint-similarity gameplay shape first.
Exact correspondence to the art's axial stretch requires richer authored
support data and is a separate choice.

This is bounded fixed-topology support work. Share the prepared interval
across geometry, carry and contact readers. Static, translation and rigid
producers keep their direct paths. M2 supplies accepted host chronology;
P3 consumes truthful source kinematics. Neither can recover motion already
discarded upstream. A local witness can land before full persistent support
or portal work; it does not certify a moving/portal publication cut.

### A shared spatial path does not imply shared movement authority

**Owners:** [PATH1/PATH2](kinematic-world-objects.md#path1--prepare-one-spatial-path-law),
with existing LDtk, brain and portal admission owners.

Combat and world duplicate waypoint evaluation because the reusable path
operation sits above world in combat. Both copies admit a coincident-point
cycle that changes cursor without consuming distance. The public initial
offset is stored but unused. Move prepared geometry, phase selection and
interval evaluation beside the core vocabulary. Bound endpoint work by
cycle reduction and prepared lookup while retaining unwrapped travel for
contact and accepted cuts. Preserve discontinuous platform wrapping.

An actor's route is another use of that geometry, with a different progress
law. Two shipped `path_ref` placements attach path state, but the native
movement method discards its advance and the patrol brain does not read it.
Make the route select ordinary intent and progress from actual arrival.
Assigning the sampled endpoint would bypass the body kernel. A shared
mutating advance-to-end API would also obstruct M2's host admission.

No new utility crate, universal motion graph or deformable-body solver is
selected. These are source-supported gaps with future native acceptance,
not gameplay reproductions or measured compile/runtime improvements.

### A curve does not choose a body's contact, gravity or posture

**Owner:** [Curved surfaces and local gravity](curved-surfaces-and-local-gravity.md),
with the existing slope, movement, pose and authoring owners. CV1–CV5 are
tentative candidates, not selected implementation work.

An ordinary robot stands its full physical shape on a slope while its
picture receives body/stance/art placement without the selected support
patch. This can leave the visual middle above the hill. Preserve accepted
contact through one bounded presentation placement; root tilt and separate
boot solving remain distinct choices. GNU additionally maps its native
hump and art differently inside their shared endpoints. Neither finding
is a reproduction of the maintainer's view, and neither is a reason to
make ordinary hills change gravity.

Source curves already compile into chains. A finite circle's center path
is offset from the source curve, so its speed and curvature do not equal
the source arc's values. Current Sanic vertex demand is sensitive to
subdivision; existing slope phase D owns that law. More samples and a
smooth normal alone do not establish correct movement.

The frame representation supports arbitrary directions, but the ordinary
walker's integration and collision code assign different cardinal roles
to some noncardinal vectors. Native arbitrary-vector material casts and
righting are foundations for a bounded adaptation, not evidence that a
radial field alone completes planetary walking. Attraction, intentional
adhesion, airborne orientation and observer up need explicit choices.
Start with existing hill appearance or one human-controlled static-circle
proof; field graphs, analytic curve CCD and general planetary navigation
remain optional. The next unrelated audit candidate below is unchanged.

## Ranked candidates for the next audit

These are research questions, not established defects or selected work.
Each starts from an existing owner and a concrete consumer. An audit is
successful if it rules out a proposed abstraction as well as if it finds one.

### 1. Geometry appears or disappears while a body occupies its region

Start with one existing closing door, toggled solid or breakable boundary.
Read the native write through collision publication and the next occupied
body query. Existing owners are
[world composition](reusable-authored-world-composition.md),
[native completion](native-action-completion.md),
[collision](collision-and-ccd.md) and
[causal world writes](causal-world-commit.md).

Ask what it means for the geometry change to be accepted: does it occur
immediately, wait for clearance, displace occupants, or report a domain
outcome? Which owner states that policy, and which current body/material
population is in scope? Keep destruction's support loss separate from a
new solid's admission. Follow one operation through blocked and occupied
cases before proposing shared machinery. W2 already owns mechanism binding;
crush reporting is deliberate. Neither is by itself evidence of a missing
geometry-change policy. This is an unproved audit question, not a new defect
or a reason for a general physics transaction framework.

### 2. Implemented contract review when a new source head is available

Read one completed cut end to end: for example, admitted input into a charge
under possession, or selected view policy into framing. Check that the old
authority was removed, positive cases remain expressible, and cost was not
moved into every unrelated consumer. Runtime results, when supplied, can
support stronger claims; a new build or native witness is not a prerequisite
for this source review.

Do not repeat an existing planned case as a newly discovered defect or
reopen a receipt without contrary evidence. An unchanged source head still
permits a new bounded audit question; it does not justify a framework merely
to fill the backlog.

### Deferred: saved content across game versions

The maintainer assigns this to next year (2027). Do not spend the current
audit or implementation queue on old-content migration, renamed-definition
compatibility or versioned-save policy. Same-session rollback, room
reconstruction and current native state still need their existing owners;
they are different questions.

### Conditional: compiler and binary costs after the planned cuts

The [compiler/build owner](compiler-boundaries-and-build-products.md)
already provides a source-based program. Static reading can find repeated
generic boundaries or an unwanted declared dependency, but ranking actual
cost and claiming a gain needs measurements: clean and incremental compile,
codegen/link time, representative binary size, feature sets, and the actual
repeated instantiations that
survive optimization.

Choose one expensive generic or dependency edge and compare its concrete,
erased or inverted forms under the same product. A crate split or trait
object can move cost instead of removing it. Do not create more packages,
type erasure or interchangeable collection APIs from file size alone.

## How to promote a candidate

Record the actual source baseline and distinguish a supported counterexample
from a shipped gameplay reproduction. State the existing owner, the first
native customer, the invariant it cannot currently express, the code that
would be removed, and the smallest proof. Measure performance only where
the proposed benefit depends on it.

Prefer refinements that make different consumers share one owned fact while
retaining their native policy. Reject a unification that adds a second source
of truth, forces unrelated consumers through an interpreter, or makes the
fast gameplay path pay for a reference model it does not need.

The order above recommends research attention. It does not move networking,
NPC work or Smash polish ahead of Ambition's selected product priorities.
