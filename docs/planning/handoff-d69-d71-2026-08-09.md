## The diagnosis, from the probe's own docstring

⭐ **It is a REPLACEMENT read as a DELETION.**
`contribute_discovered_hidden_blocks_to_overlay` promotes a struck `BonkOnly`
block to a `Solid` by pushing **the block's own name** into
`removed_block_names` **and** the promoted block into `blocks` — *the same name,
the same box, the same `GeoId`*. `sync_removed_block_visuals`
(`crates/ambition_render/src/rendering/world.rs:1335`) reads only the first half
and despawns the sprite the second half is asking for.

⇒ **so the fix is probably NOT "add an added-block reconciler".** The narrower and
truer statement is: **a name appearing in both lists is a replacement, and the
removal half must not win.** ⚠ the ledger row still frames this as a missing
reconciliation half — **the probe's framing is better and was found later.**

⚠ **`spawn_room_visuals` (`:75`) draws `world.blocks` at ROOM LOAD only**, so
whatever you do must work mid-run.

⭐ **the engine already draws overlay-added blocks — for `gate_solids` only**, in
`sync_lock_wall_visuals` (`:1154`). That is precedent, and it means the capability
exists with one adopter rather than not existing.

## Traps already paid for — do not rediscover these

1. ⛔ **Ordering.** If both reconcilers run in the same frame, order decides the
   outcome. **Assert the order in a test** — a cross-schedule `.after` is
   *silently vacuous* in Bevy. ⭐ **copy the pattern from**
   `game/ambition_app/tests/room_boundary_unclaimed_views.rs::the_room_transition_cover_is_ordered_after_the_unclaimed_census`
   (landed 2026-08-09): it builds the **real** app graph, asserts the edge, **and**
   asserts each set has members *in that schedule* — the second clause is the
   anti-vacuity guard a name-only edge would slip past.
2. ⛔ **A block seeded right after `settle_until_playable` is silently wiped.**
   Activation keeps emitting `RoomLoaded` for two or three more frames plus a
   `Manual` room reset, and both re-arm block state. **Settle ~60 frames first**,
   and assert the seed took *before* the action so a wiped seed fails a
   pre-assertion instead of going vacuously green.
3. ⚠ **`drawn_image_opt` returns `Option` on purpose** — *"there is no visual"* is
   an **answer** here, not a broken probe. Do not "fix" it back to a panic.
4. ⚠ **Exactly ONE hidden block exists in the game.** That is not an argument
   against the fix — the same gap silently drops every future overlay-added block
   — but it does mean the probe has one concrete target.

## Why the row exists

From a 290 s profile capture of the maintainer's own play
(`target/profiles/desktop-timeline-run-20260808T185222Z/game-stderr-stamped.txt`):

```text
room transition … BEGIN   seq=1   mary_o_1_1 -> mary_o_1_2   t=257.006s (retired 257.040)
   …the ONLY transaction in 290 s.        mint_sequence is a monotonic global, never reset.
music target flips        t=208.92s and t=210.69s     ← rooms plainly changed
190 unclaimed-body warnings in 20 bursts, t=72s…273s  ← NONE inside that one cover window
```

⇒ **Not one magenta stand-in was drawn while a transition cover existed.** So the
maintainer's *"changing rooms flashes magenta squares"* **cannot** be explained by
cover timing — which is what D46 spent its whole life on. **An uncovered room
change explains it completely and needs no other defect.**

## The order of questions, and it matters

1. ⭐ **Is it still reproducible?** The capture is from `40d896593` and a great
   deal has landed since. **If it is already fixed, that is the best outcome** —
   say so and close D71.
2. If reproducible: **which route changes rooms without opening a transaction?**
3. ⛔ **Do not fix it in the same commit as the instrumentation.** A bypass is a
   composition question; the number comes first.

⚠ **Start from the "a room changed" signal and ask which of those opened a
transaction** — *not* from the transition code forward. D46 spent its entire life
reasoning forward on the wrong branch, and what settled it was reading a log.
Independent signals that a room changed: the music-target flip, `RoomLoaded`, the
active room metadata.

✔ **A known-good control**: `app_it` crossings through `proving_grounds_hub_door`
*do* produce covered transitions. Whatever route the maintainer used, it is not
that one.
