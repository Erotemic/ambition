  through `ControlFrameLatch`, which ORs sub-tick press edges together so a tap
  between two ticks is never swallowed. **A secondary seat has no latch.** On a
  fixed-tick host a very short player-two tap is missed.
  This is a FAIRNESS asymmetry in the couch versus mode — two people on two pads,
  and one of them has forgiving input and the other does not. It was written down
  as bounded and named rather than hidden, which is right, and it has been true
  since the second seat landed.

  buffered edges on the transition to `Fighting`, so the very first frames of a
  round are exactly where a dropped tap is most likely and most visible.

  clock by `populate_secondary_slot_controls` and drained on the TICK clock by
  `publish_latched_slot_controls`. The primary seat's two-system shape, installed
  under the same `sim_is_fixed_tick()` condition and ordered the same way,
  because a frame-stepped host has one frame per tick and nothing to bridge.
  ⚠ **slot 0 is deliberately skipped** — it already drains `ControlFrameLatch`,
  and latching it twice would hold one press across two ticks. A test asserts
  seat two's edge does NOT appear in slot 0 for exactly that reason.
  ⚠ **a pause CLEARS rather than drains.** `take` retains levels by design; a
  seat that has stopped being driven must not hand a held direction to the tick
  after the pause, so the not-gameplay branch calls `reset`. Same rule the
  primary seat already followed.
  ⚠ **the sample no longer writes `SlotControls` directly under fixed tick** —
  doing both would be the sample racing its own latch, and the tick would see
  whichever system ran last.
  → three tests: the sub-tick tap survives, seats do not leak into each other,
  and a reset drops held levels rather than only edges. 24/24 versus tests stay
  green, including the four-pad one.
  ⛔ **and the fix opened a rollback hazard that the fix then had to close.**
  The drain runs in the SIM schedule, which under a rollback host IS the GGRS

  (`TextFont { font_size, ..default() }`), which is the same thing the bare path
  resolves, so the difference is elsewhere in `ambition_menu`.

  ⊘ **and it is not the font ATLAS filling up either** (the fourth elimination).
  Putting `· —` at the START of the launcher TITLE — the first menu text laid
  out, at the largest size on screen — tofus both. So it is independent of
  position, of size, and of how much text preceded it.

  ⊘ **and it is not `TextFont` itself** (the fifth elimination). Spawned side by
  side on the same route in one frame — one bare `Text::new` with NO `TextFont`,
  one with an explicit `TextFont { font_size: 24.0, ..default() }` — **both
  render `·` and `—` correctly.** So passing the component explicitly, which is
  the one thing `ambition_menu` visibly does differently, is not the cause.

  ▢ **remaining: WHICH difference.** Five candidates are dead (the font asset,
  the string, the capture/route, the atlas, `TextFont`). What is left is the rest
  of the menu spawn — `text_node()`, `MenuTextHeightFraction` and its scaler,
  `TextLayout::new_with_justify(..)`, `ZIndex`, and the fact that menu text is a
  CHILD of the menu body rather than a root node. ⚠ the menu path renders ASCII
  fine, so it has *a* font; it is not a dangling `Handle::default()`.

  ⊘ **and it is not a byte-vs-char truncation** (the sixth, and the hypothesis
  that best fit the symptom — ASCII survives, multi-byte does not). There is no
  `as_bytes`, `truncate`, slice-by-index or char counting anywhere on the path:
  `presentation.footer.clone()` → `MenuNode::Text { text }` → `Text::new(text)`.
  The string arrives intact.

  **The bisect was RUN, and it eliminated the components too** — plus produced
  the strangest and most diagnostic fact of the lot.

  * ⊘ **not the components.** Removing ALL FOUR at once — `TextFont`,
    `MenuTextHeightFraction`, `TextLayout` and `ZIndex` — still tofus.
  * ⊘ **not a warm-up or atlas-lag race.** `--warmup 400` still tofus, and three
    identical captures hash the same, so it is fully deterministic.
  * ⛔ **but adding an unrelated SIBLING `Text` to the same parent makes the
    title render CORRECTLY.** Inserting
    `body.spawn((Text::new("CHILD-BARE · —"), TextColor(..)))` immediately before
    the real text spawn fixed the title's `·` and `—` — while the inserted child
    itself still tofu'd. Nothing else changed.

  * ⊘ **not span inheritance either** (the seventh). If an ancestor carried
    `Text`, these children would be treated as SPANS and inherit its font, which
    would have explained the sibling effect exactly. No ancestor in
    `spawn_bevy_ui_menu_with_assets` carries `Text`, `TextFont` or `TextColor`.

  * ⊘ **not fractional font sizes** (the eighth). `reference_pixels()` produces
    e.g. 31.68px where every working bare spawn used an integer. Rounding it in
    `pixels_at` still tofus.
  * ⊘ **not a per-frame respawn** (the ninth) — the theory that best explained
    the sibling clue: if the tree rebuilt every frame, every text would always be
    "first" and `--warmup` could never help. Instrumented: the launcher rebuilds
    **twice** in a whole capture, not per frame.

  ✔ **and that instrument found something small and real — which was the
  INSTRUMENT'S OWN, and is CLOSED.** The launcher rebuilt twice because
  `ShellActivationId` went 1 → 2, and the second activation was `capture_scene`
  sending `GoTo` unconditionally onto the route the shell's own
  `initialize_shell` had already activated. Not a product defect: no player
  reaches that state. Fixed in the same commit that recorded it (`3eeb5ead9`) —
  `go_to_route` now waits for the router to settle and navigates only if the

  Verified 2026-08-01: `ShellCommand::Initialize` is guarded by
  `self.initialized` (`router.rs:252`), so the shell mints exactly one
  activation per cold start. ⛔ do not re-open this as "activated twice is the
  shape S23's every-frame re-minting had" — it is the eighth measurement
  artifact of the run, and the writer, not the reader, held the answer again.

  → **that is the clue to chase.** A per-parent or per-(font, size) effect where

  all died. It points at Bevy's text pipeline — atlas keying, font-face
  resolution, or `ComputedTextBlock` sharing — rather than at `ambition_menu`

### Still open

- ▢ **F0e** `DeathPolicy::Unbounded` is now *reachable* and still has no
  production caller. Selecting it for the duelists turns versus from HP
  depletion into pure knock-off, which is the genre — but only if knockback

  frames. 420px/s sustained for the half-second window would be ~210px; it
  travelled 7% of that.

  Two things this cost, worth recording because both are the same mistake:
  the FIRST measurement reported the four-second maximum displacement and got
  `dx = -295px` — the CPU walking home to the middle of the stage. A knockback
  measurement has to end before the victim gets its steering back, or it
  measures the brain. And the number to watch was never "how far" but "does it
  leave the ground": knockback resolves to roughly `(322, -269)` here, so the
  upward component is real and 18.8px of rise means it is being eaten, not
  omitted.

  So F0e is NOT a tuning row. Making the number bigger multiplies something that
  is being discarded. Find what discards it first.

  **Found, and it is the fourth instance today of the same shape.** The per-frame
  trace shows `vel.x` falling by exactly 62.5px/s every frame — a constant
  3750px/s², which is `AIR_STOP_ASSIST` to the digit. That is the airborne
  hands-off deceleration, and it decays a body toward `carried_run`, the
  "carried-momentum floor". `carried_run`'s own doc says the floor exists so
  coasting "must still not bleed away speed the WORLD imparted (**portal flings,
  knockback**)". Knockback is named there. It was never wired: the portal transit
  adapter is the ONLY writer of `carried_run` in the repo, so a launched body's
  floor is zero and the launch is erased in seven frames.

  A mechanism exists, its documentation names the exact case, and nothing
  connects the case to the mechanism — the same sentence as
  `DeathPolicy::Unbounded`, as the "ONE gate every policy publishes through",
  and as `RoomMetadata::mode`.

  **Tried, measured, and NOT landed.** Setting `carried_run` to the launch's
  side component — the way the portal fling does — works exactly as intended in
  isolation: same smash, same fighter, same lip, `|dx|` 15.5px → **111.8px**,
  and they leave the stage. The per-frame trace is the whole story — `vel.x`
  used to fall 62.5/frame to zero by t+7 and instead holds flat at 329.7 while
  gravity does its work on `vel.y` alone.

  It is a CORE FEEL change touching every struck body, not just fighters, so it
  went to the full suite. The suite found two things, and the first was a real
  defect in the change itself.

  ✔ **The defect (mine), found by reading rather than by the suite.** An actor
  killed by the blast zone ran the ordinary death path, and
  `RespawnPolicy::InPlace` respawns a body AT ITS CURRENT POSITION — which, for
  a body that just left the world, is still outside the world. It dies again on
  the next tick, respawns again, and the room acquires a body whose entire
  behaviour is dying. `sandbag_finite` is the one archetype that authors
  `InPlace`, so it is the one archetype for which "gone" and "the authored
  policy" disagree — and it is now the subject of the test.

  I first blamed this for the oracle's stalled clock. It is NOT: applying the
  fix left the oracle's numbers byte-identical (300 / 59 / 64), which is what
  disproved it. Worth recording, because a plausible cause that changes nothing
  is the cheapest kind of wrong answer to keep believing.

  Landed as `KillDisposition` — a named decision (`RespawnInPlace` / `Defeated`
  / `GoneFromTheWorld`) rather than an inference from the order of an
  `if`-chain, red-probed by deleting the `LeftTheWorld` arm. Gone means gone:
  no respawn timer, and no bounty coin or death explosion either, since those
  would land in the void where no player can walk.

  ✔ Also landed: the blast hit is gated on the body being ALIVE. The gate is a
  position test that re-fires every tick, so a corpse outside the world was
  writing a lethal hit per frame that the damage pass silently refused — a
  per-frame cost with no visible symptom, which is worse than a visible bug.

  ⛔ **AND THE FIX IS NOT LANDED.** Reverted. The oracle's route still completes
  (all four events by frame 164, same ~5.7s wall clock as clean), but GGRS
  advances **300 times in 600 harness steps** where a clean tree advances more
  than 600. Isolated to the single `*carried_run = …` line by disabling just
  that line and watching the oracle go green — so the line is certainly the
  cause.

  ⛔ **MY EXPLANATION OF WHY WAS WRONG, and measuring it is what showed that.**
  I wrote here that conserving the launch pins a struck body against its
  attacker, so it is re-hit as its i-frames lapse, and the resulting hitstop —
  a GLOBAL clock rule, `scale = 0.0` whenever the PRIMARY player's
  `hitstop_timer` is live — starves the simulation clock. Plausible, and the
  clock rule is real (`emit_player_time_intent_system`). But instrumenting the
  oracle to count body-frames of each reaction timer says the opposite:

  | | hitstop | hitstun | i-frames | result |
  |---|---:|---:|---:|---|
  | clean | 70 | 96 | 496 | passes |
  | carried floor | **47** | **85** | **381** | fails |

  Hitstop went DOWN by a third. FEWER hits land, not more — carried momentum
  carries a struck body AWAY from what hit it, which is the opposite of
  pinning. So the slowdown is not hitstop, and the mechanism is still unknown.

  What is known: both runs reach `last_simulated_frame: 64` with `load_runs:
  59`, and the advance count differs by almost exactly 2×. Same frames reached,
  same rollbacks issued, half the schedule runs. That smells discrete rather
  than continuous — a stepping or accumulator difference — and it is where the
  next person should start rather than re-deriving the hitstop story.

  ⚠ Recorded at length because a plausible cause that survives in a document is
  worse than no cause at all: it is what the next reader builds on.

  What the fix NEEDS is a release condition: the floor is momentum you were
  given while you could not act, so it must be surrendered the moment you can.
  Bounding it to the recoil-lock window is the shape, and it needs plumbing the
  two damage callers do not have today (`BodyCombat::decay_reaction_timers` is
  shared but never sees the flight cluster). Do NOT simply re-apply the line;
  the pinning is a real gameplay defect and would ship with it.

  Landed from this investigation, because both are correct with or without the
  carry: the OOB in-place respawn loop above, and the alive-gate on the blast
  hit.

### The architecture decision, argued and settled (2026-07-28)

**→ THE PLAN LIVES IN
[character-preparation-finalization-plan.md](character-preparation-finalization-plan.md).**
Three rounds of argument, three refusals accepted, an execution order that keeps
a bisect possible, and the caveats that only surfaced in round three (`finish`
vs `cleanup`, manually-driven apps needing explicit finalization, hot reload as
a separate transaction, transactional publication). The summary below is the
ledger's pointer; the doc is the detail.

The reviewer proposed a `PreparedBodyBlueprint` + a `BodyUnderConstruction`
marker + a `PreparedMatchPlan`. I pushed back on three points and the reviewer

- ⛔ **No new stored authority.** A blueprint carrying action set / moveset /
  motion / hurtboxes / provider beside `PreparedCharacterDefinition` is R-g's
  seventh authority with a new name. A borrowed view or a function return is
  fine; a stored one is not.
- ⛔ **No `BodyUnderConstruction` marker.** Its safety is `Without<..>` in every
  present and future body query — the identical shape to
  `apply_worn_character_gameplay` silently not matching seated bodies (which IS

  must be deferred, defer a REQUEST rather than publishing an incomplete body.
- ⛔ **Rollback cannot sample device discovery.** A plan assembled from live
  devices inside a rollback tick does not reproduce on resimulation. External
  topology is frozen BEFORE the session; only deterministic selections and
  activation phase live inside it.

  reviewer's intermediate — one resolver taking `(&prepared, &catalog)` — works

- ✔ **AC1 — a host-code character could author a `ranged` verb, and BOTH owners

  mistake. It costs an over-declared cue in the load inventory, which is cheap and
  honest about what the author wrote.

   `apply_to_body` writes `max_health`/`mass` only on `Some`, so a character
   authoring neither keeps the PREVIOUS persona's values. Needs a body-physical
   ORIGIN to fall back to (`new persona override, else host baseline`), never
   "absence means keep the last override". AD4 fixed the geometry half of this
   family; this is the health/mass half and it is the harder one.

5. **▢ AD8 — the registered-character voice floor.** Prepared voice reaches
   ambient barks only; on-hit and provoked barks fall through to engine-generic
   text, so a third-party character speaks in its own voice until it is hit.
   Either pass the registry into those paths or narrow the doc — the current doc
   claims a floor it does not provide.

6. **▢ AC23 — a session install can LAUNDER an unhealthy session.** One of four
   call sites guards it, and its comment explains exactly why it must. Make the
   seam state the fact rather than relying on each caller remembering.

7. **▢ AC19 / AC22 / AC21** — the small ones: demote the DebugLabel spacer to a
   lint now that the runtime places every family; give the exit oracle a fixture
   room it owns; clear the three `ambition_app` warnings.
