## S30 — recon for the incoming CRATE RENAME campaign (2026-08-01)

Jon has an untracked `docs/planning/engine_rename_campaign.md` naming the
renames (`ambition_platformer2d_core` → `ambition_platformer2d_core`, `ambition_platformer2d_world`
→ `ambition_platform2d_world`, `ambition_portal2d` → `ambition_portal2d`, …). It
says the renames "can mostly be accomplished with sed." Two of them cannot, and
both are cheap to know BEFORE the sed rather than after.

⛔ **1. A crate name is a ROLLBACK WIRE-FORMAT FACT today.** `descriptor()`
stores `std::any::type_name::<T>()`, `schema_dump()` writes it, and
`schema_fingerprint()` hashes the dump — so renaming a crate moves
`SnapshotSchemaFingerprint` for every component that lives in it, and two peers
with BYTE-IDENTICAL wire formats then refuse to agree.

That is the *same defect* v5 fixed one level down. `registry.rs:33` says it in
its own words: hashing the registration OWNER "made 'which module registered
this' a wire-format fact", so v5 stopped hashing it. The crate path inside
`type_name` is the same category of organisational label, and it is still
hashed. Measured impact: **94 of the 352 lines** in
`game/ambition_app/tests/rollback_schema_baseline.txt` name a crate on the
rename list (`ambition_portal2d` 31, `ambition_platformer2d_core` 27,
`ambition_platformer2d_shared_tangle` 26, `ambition_platformer2d_world` 8, plus
`ambition_platformer2d_runtime`/`ambition_platformer2d_ldtk`).

  ▢ **decide which, and it is a real fork, not a formality:**
    (a) regenerate the baseline and bump `GGRS_ROLLBACK_SCHEMA_VERSION` —
        honest, one commit, and concedes that renaming a crate is forever a
        compatibility break; or
    (b) hash the type's FINAL SEGMENT plus its module path below the crate, so
        the fingerprint stops caring where a type is packaged — which is what v5
        already decided for owners, applied consistently. ⚠ this makes two
        same-named types in different crates collide, so it needs the
        `RollbackRegistry` duplicate-name check to stay the thing that catches
        it (it already rejects duplicate `name`s).
    The baseline regenerates either way; only (b) makes the NEXT rename free.
    → **moved to [awaiting-maintainer-decision.md](awaiting-maintainer-decision.md)
      2026-08-01, because it stopped being free to defer.** The
      `ambition_geometry` carve landed; the snapshot codec is the next general
      thing stuck in the platformer core, and moving it rewrites the
      fingerprint. That row carries the recommendation — (b), because the engine
      is at the START of a carve campaign and (a) prices every future move as a
      compatibility break — plus the probe that choosing (b) obliges.

⚠ **2. `const OWNER: &str = "ambition_platformer2d_runtime"` in ten files** is not caught by
a rename of the crate DIRECTORY, but sed on the string catches it, and since v5
it is cosmetic — it is not hashed and nothing reads it. Named here only so the
inconsistency is deliberate rather than missed.

✔ **the rest really is sed-shaped**: no crate on the list appears in any `.ron`
or `.json` under `content/` or `assets/`, so no authored content names a crate.
46 hits across `scripts/` are ordinary paths.

## S48 — ▢ `locomotion.x` has TWO conventions and nothing enforces either (2026-08-01)

Found while chasing the ladder self-KO (the row above: *"the brain emits FULL
LEFT for three decisions and the body keeps accelerating right"*). ⚠ **this is
NOT confirmed as that bug's cause** — see the last paragraph — but it is a real
defect in its own right, and it was invisible because the two conventions agree
in the only configuration anyone tests.

**The contract, stated in the kernel** (`ambition_platformer2d_core`,
`LocalAxes`):

> *"Controlled-body-local axes: `+x` local side/right, `+y` toward the feet. The
> frame every unqualified movement verb is written in. **Produced exactly once
> per controller tick by resolving raw `ScreenAxes` against the body's current
> `AccelerationFrame`.**"*

**Who obeys it.** `brain/player.rs` says so at the write —
*"unqualified direction is controlled-body-local … Downstream movement code
should not re-resolve this"*. `brain/smash/emit.rs` uses
`obs.side_face_toward_target()`, a gravity-perpendicular side sign, and its
comments are explicit that this is *"correct under any gravity"*.

⛔ **Who does not.** `brain/fighter/decision.rs::apply_movement` — the FB brain,
the one the ladder runs — writes RAW WORLD X into that field, in every verb:

```rust
let toward = foe.pos.x - view.self_view.pos.x).signum();   // world
frame.locomotion.x = toward;                               // ...into a LOCAL field
// and Recover:
let home = ((bounds.min.x + bounds.max.x) * 0.5 - pos.x).signum();
frame.locomotion.x = home;
```

⛔ **and the conversion that should catch it is a REINTERPRETATION.**
`ActorControlFrame` → kernel does `LocalAxes::from_vec(self.locomotion)`, which
copies the components and renames the type. There is no resolution against the
`AccelerationFrame` the doc names, so a world-space vector becomes a
body-local one by assertion. The type says the transform happened; nothing
performed it.

⚠ **the same brain resolves gravity ELSEWHERE**, which is what makes this an
inconsistency rather than an omission: `fighter_from_self(view, gravity_down)`
builds the shadow model against the gravity frame, and `is_punishable(foe,
me.gravity_down)` reads it. The rollout reasons in the body's frame; the emit
does not.

▢ **why it has never been seen**: under screen-down gravity on a flat stage,
local side IS world `+x`, so both conventions produce the same number. The
divergence needs rotated gravity or a surface-walking frame — which the Noether
Chamber has and the ladder does not. So this is LATENT, and the ladder trace
above still needs its own answer.

✔ **step 1 DONE — the FB brain now emits in the body's frame.** Both writes go
through `view.self_view.acceleration_frame().to_local(world_delta)`, which is
the resolution `LocalAxes`' own doc names. Byte-identical under screen-down
gravity (457 existing tests unchanged), and `Recover`'s stage-centre delta is
resolved the same way rather than compared on raw `x`.
→ pinned by `every_lateral_this_brain_emits_is_in_the_bodys_own_frame`: with
gravity pointing world-left the foe sits on the body's gravity axis, so no
sideways throttle can close on it and every emitted lateral must be zero.
Probed by restoring the world-space sign — forty ticks of `1.0`.
