  ```rust
  clusters.kinematics.vel = body.vel;
  ```

  in exactly the right place with exactly the right operation — `apply_pad_impulse`
  decomposes into the ride frame and, when the impulse leaves the surface, sets
  `body.vel` AND `motion = Airborne`, "keeping the momentum perpendicular to the
  impulse axis". A spring launching a running body is the same problem as a hit
  launching one. **Knockback is the only external impulse that does not go through
  it.**
  ⚠ **but it is not a drop-in, and the difference is a rule not a tuning value.**
  A pad's tangent-dominant case only replaces `v_t` *"when that makes the body
  faster"* — a booster declines to slow you. A hit must not decline: knockback
  along the run overrides it. So the operation wanted is a sibling,
  `apply_external_launch`, that shares the frame decomposition and drops the
  faster-only guard.

- ▢ **G1 PICK 7 (found 2026-08-03 by measuring, not by reading): the rollback
  SCHEMA is a per-frame budget line, and nothing in the repo treats it as one.**
  The frame-cost probe found a **fixed ~4.3 ms/frame floor** under GGRS —
  snapshot save plus checksum — paid on every frame whether or not a rollback
  occurs, and **1.6× the 2.65 ms cost of simulating the frame at all**.
  ⭐ **that puts two of my own workstreams in direct tension, and I had been
  running only one of them.** The rollback coverage sweep pushes monotonically
  toward registering MORE (its ceiling went 66 → 23 today, and I added three
  resources to the registry). The frame budget pushes the other way: every
  registered entry is serialized every frame, forever, in the shipped Ggrs
  composition. **Registration has been treated as free correctness. It is not
  free, and the sweep has no notion of its own cost.**
  ⚠ **this is NOT an argument to register less** — an unregistered resource that
  should be registered is a desync, which is worse than a slow frame. It is an
  argument that the two need to be *weighed*, and right now only one of them has
  a number.
  ▢ **the discriminating measurement, cheap and not yet run**: does the 4.3 ms
  floor scale with the ENTITY POPULATION or with the SCHEMA SIZE? Run the same
  probe in a near-empty room against `combat_calibration_lab`. Population-scaling
  means the cost is snapshot volume and the schema is not the lever;
  flat means it is fixed per-registration overhead and the schema is exactly the
  lever. ⛔ do not build either fix before that number exists — that is precisely
  the mistake the LDtk cache above records.
  ⛔⛔ **THE RELEASE NUMBERS ARRIVED AND THEY CUT THIS ROW'S PREMISE DOWN.** Same
  probe, same room, `--release`:
  | fixed 60Hz, no rollback | 2.17 ms/frame |
  | sync-test distance 1    | 4.32 ms/frame |
  | sync-test distance 2    | 6.94 ms/frame |
  | sync-test distance 4    | 11.92 ms/frame |
  **~2.5 ms per resimulated frame over a ~1.8 ms fixed floor** — and the number
  that matters is the comparison I could not make in debug: a resimulated frame
  costs **2.5 ms against a 2.17 ms plain simulation step**, so moving the state —
  save plus restore — is about **0.35 ms.**
  ⭐⭐ **so the cost of a rollback is RE-RUNNING THE SIMULATION, not the schema.**
  The claim I opened this row with — "every registered entry is a per-frame budget
  line" — is true and is roughly a seventh of what I implied. Registering a
  resource is not free, but at 0.35 ms for the entire current schema it is
  nowhere near the lever I called it, and **an unregistered resource that should be
  registered remains strictly worse than a slow frame.** The sweep's direction was
  never in question; my sizing of the counterweight was wrong, by measuring it in
  a debug build and reasoning about a shipped one.
  ⚠ **what the 1.8 ms floor actually contains is still unseparated**: save-once
  plus checksum, and **the checksum is sync-test-only**, so the floor a shipped
  netplay session pays is strictly smaller than 1.8 ms and possibly much smaller.
  That also re-explains the 44.3 s test — a large part of its cost is checksum
  work that exists to catch desyncs and has no shipped counterpart at all.
  ▢ **what survives, and it is worth having**: at 60 Hz the budget is 16.67 ms and
  a plain frame is 2.17 ms, so a **6-frame rollback costs ~2.2 + 1.8 + 6×2.5 ≈ 19
  ms and misses the frame.** The constraint is real, it is about simulation
  throughput rather than snapshot size, and **it is now measurable in one command**
  — the probe is kept as `#[ignore]`d instrument
  `probe_what_a_rollback_frame_costs`, with these numbers in its doc comment.
  ▢ the population-vs-schema discriminator above is now LOW priority (it can only
  move the 0.35 ms), and the useful successor question is **what the 1.8 ms floor
  splits into**, because only the non-checksum half is a shipping cost.
