D3's sequencing puts this BEFORE the P5 rebind-capture UI, so the rebind rows are

**⇢ A1's activation half is SCOPED (2026-08-06). Do not re-derive this.**
`dispatch_menu_action` is ALREADY one dispatcher — the duplication is one step
earlier, at "which action did the user just choose", and there are THREE routes
into it where there should be one message:

1. **pointer** — `MenuActionActivated<MenuPageAction>` (published by the
   renderer's bridge) → `grid_menu_action_activated` → dispatch. ✔ already an
   event; this is the shape the other two should take.
2. **keyboard/controller, Items page** — `grid_menu_nav` resolves
   `owned_item_action(idx)` from the cursor and dispatches INLINE
   (`grid_backend.rs` ~564). The cube has its counterpart.
3. **keyboard/controller, System page** — `system_focus_nav`, which is already
   SHARED by both backends (one function, so the two frontends do not disagree)
   but dispatches internally.

⭐ so the edit is: routes 2 and 3 PUBLISH `MenuActionActivated<Action>` instead of
dispatching, and the existing consumer becomes the only dispatcher. That also
shrinks `system_focus_nav`'s ~18-parameter signature by every param it holds
purely to dispatch (`owned`, `commands`, `players`, `mana_q`, `heals`, and the
dispatch half of `sfx`), which is the real reason both backends bundle
`SystemParam` structs to stay under Bevy's 16-param ceiling.

⚠ **NOT every submit is an activation.** `grid_backend.rs:528` — SELECT on the
tab bar drops focus into the body — is structural navigation and must stay in
nav. The distinction is worth encoding rather than discovering per-branch.

⚠ **ordering**: `grid_menu_nav` runs in `MenuNavConsume`; the activation
consumers run `.after(BevyUiMenuInteractionSet)`. A message published by nav must
be consumed the SAME frame, per the `InputSet` contract ("an edge produced this
frame is consumed this frame, never at worst a frame late") — so check the
relative order of those two sets before assuming it holds.

▢ **A2 — D5: any seat pauses, and that seat drives the menu.**
⚠ today's behaviour is NOT what the handoff first claimed. The pause menu reads
`MenuControlFrame`, which `populate_menu_control_frame_from_actions` fills from

already reads it. The world still stops for everyone; the one piece of new state
is which seat OWNS the open menu, so `drive_shell_pause_menu` reads that seat's
frame instead of the global one.

▢ **A3 — D2: input FILTERING is keyed to the pad, bindings stay machine-wide.**
`populate_secondary_slot_controls` and `populate_control_frame_from_actions` both
pass the one global `&user_settings.controls`, so player two's drifty 360 pad
runs on player one's DualSense-tuned deadzone. `ControllerProfileId` already
carries the per-pad calibration (360 = wider deadzones + worn-trigger hysteresis;
PlayStation = tighter) — it is the CHOICE that is global, not the table.
⛔ this row CLOSES PA1's "per-seat presets" item by narrowing. Do not build
per-seat presets or per-seat binding overrides; Jon ruled those stay
machine-wide.

▢ **A4 — D4: dialogue claims the TALKER, not the world.**
`GameMode::Dialogue` leaves the suspend set (`apply_suspended_time_scale_system`
under the `gameplay_suspended` run condition, `player_schedule.rs`), and
`DIALOGUE_CONTEXT` — already declared by `declare_in_session_input_contexts` —
becomes the whole gate. ⚠ `dialogue_still_stops_the_world_as_well_as_claiming_
the_input` pins the OLD behaviour and must be re-aimed, not deleted. The
per-experience opt-in to stop the world STAYS (Jon 2026-08-03: both must be
expressible). ⚠ `RoomTransition` and `Cutscene` are explicitly not the same

▢ **A5 — dialogue CONTINUITY, which is what A4 costs.** Design and Jon's verbatim
words: [`engine/dialogue-continuity.md`](engine/dialogue-continuity.md). Once the
world keeps running, a conversation has to keep being POSSIBLE:
- it BREAKS on damage and on the participants separating;
- it HOLDS its participants in station if they are capable of it;
- a break BARKS, because a conversation that silently vanishes reads as a bug.
⭐ symmetric, from the actors' side — *"both characters should hover"*. Any
implementation that asks whether the PLAYER can still talk has already got it
wrong. ⛔ the one missing authority is "can this body hold station": `can_fly`
