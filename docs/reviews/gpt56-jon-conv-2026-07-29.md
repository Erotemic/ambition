Yes—this is a deep architecture problem, but not because we need to invent software modularity from scratch.

The repository already contains most of the **vision**. What it lacks is a sufficiently strong theory of **how the engine grows**.

## The current documents are directionally right

The existing architecture says:

* another platformer should be possible through a provider and thin host;
* domains should own their state, systems, schedule sets, and plugins;
* simulation and presentation should be separate;
* runtime should assemble domain plugins rather than implement their leaf systems;
* games should own named content and product policy;
* the engine should remain Bevy-native.

That is a good target.

The problem is the special status granted to the **“simulation heart.”** The documentation treats `ambition_actors` as the place where all the authority-woven pieces finally come together. In practice, that has turned it into the place where almost everything eventually comes together.

I counted **27 direct `ambition_*` dependencies** from `ambition_actors`. It now contains or coordinates actor simulation, character construction, combat integration, world construction, LDtk adaptation, persistence, menu content, audio, music, dialogue, cutscenes, assets, encounters, bosses, session lifecycle, and presentation publication.

That is not because the agent is careless. It follows naturally from the current architecture:

> Every cross-domain feature eventually needs the simulation heart, so every cross-domain feature eventually grows the simulation heart.

A one-time crate split will not fix that.

## The key conceptual mistake

The repository has correctly insisted on:

> one body, one path

But that has gradually become conflated with:

> one crate owns the complete path

Those are not the same thing.

In an ECS engine, one body can follow one coherent execution path while different domains contribute systems to that path:

* movement owns movement state and stepping;
* combat owns move playback and hit resolution;
* control owns actor-local intent;
* perception owns observations and memory;
* equipment owns capability overlays;
* world collision owns spatial queries;
* lifecycle owns body birth, restart, and retirement.

Their systems can operate on the same entity and participate in the same ordered schedules without living in one crate.

The **engine’s heart should be a protocol and schedule, not a crate**.

That is the architectural shift I think Ambition needs.

## Have Unity and Godot already solved this?

They have solved important adjacent problems.

Unity uses packages and feature sets to distribute reusable engine, editor, runtime, asset, and tooling functionality. Unity explicitly presents packages as self-contained units and feature sets as collections of related packages. ([Unity Documentation][1])

Godot supports engine modules that can be enabled or disabled and can add functionality without directly modifying core code. GDExtension provides a distributable native extension path without requiring consumers to rebuild Godot itself. ([Godot Engine documentation][2])

Those systems establish:

* stable extension surfaces;
* installable feature units;
* product-facing discoverability;
* a distinction between core functionality and optional extensions.

They do **not** hand us an obvious answer for decomposing a deterministic Rust ECS platformer engine. They primarily solve extension, distribution, and product integration. Copying their internal nouns would not automatically produce Ambition’s ideal architecture.

Bevy is more relevant structurally. Bevy describes plugins as scoped collections of components, resources, and systems, with smaller scope generally preferred. Plugin groups combine those capabilities into convenient larger compositions; `App` and `SubApp` provide explicit lifecycle and world boundaries. ([Bevy][3])

Rust adds something Unity and Godot’s ordinary game-facing architectures do not emphasize to the same degree:

* compiler-enforced dependency direction;
* independently buildable capability libraries;
* explicit public APIs;
* zero-cost generic composition where useful;
* precise control over which capabilities a consumer links.

So there is a genuinely interesting opportunity here. Ambition can potentially be more compositionally elegant than the premier engines rather than merely recreating their monolithic core with Rust syntax.

But ECS does not make the problem disappear. Cross-domain interactions remain real. The architectural question is where those interactions live and how they avoid becoming another central integration blob.

# A more holistic target

I would replace the current “seven layers plus simulation heart” picture with a **federated capability engine**.

## 1. A very small actor protocol

“Actor” should name the minimum shared protocol that lets capabilities cooperate:

* stable identity;
* body identity and lifecycle;
* control authority;
* simulation scope;
* construction and replacement transactions;
* common schedule phases;
* perhaps a small amount of universal spatial/body vocabulary.

It should not own:

* combat;
* dialogue;
* inventory;
* music;
* menus;
* persistence;
* LDtk;
* boss behavior;
* sprite loading;
* encounter rules.

An actor is then not an object implemented by `ambition_actors`. It is an ECS entity participating in installed capabilities.

## 2. Domain-owned capability plugins

Each substantial domain owns its complete vertical capability:

```text
vocabulary
authoring schema
prepared representation
live state
commands and facts
systems
schedule sets
rollback registration
inspection/read models
owner plugin
```

Examples:

* movement;
* combat;
* perception and brains;
* equipment;
* projectiles;
* dialogue;
* encounters;
* persistence;
* world collision;
* interaction;
* character presentation.

A domain should not require `ambition_actors` to install or complete it.

## 3. Explicit integration plugins

Cross-domain behavior should be represented as an integration, not absorbed into a universal heart.

For example:

```text
combat emits HitResolved
    ↓
body-damage integration applies knockback and vitals changes

equipment emits CapabilityLoadoutChanged
    ↓
combat-equipment integration rebuilds the combat overlay

world emits ContactFacts
    ↓
movement-world integration updates grounded/support state
```

Often the consuming domain can own the reaction. Where neither domain is the clear owner, create a narrowly named integration plugin.

This does risk producing many adapters. That is still better than hiding every adapter in one monolith, provided integration plugins obey rules:

* depend only on the domains they join;
* own no competing domain authority;
* expose no giant universal service interface;
* remain optional where the joined capability is optional;
* have an explicit schedule relationship;
* remain independently testable.

## 4. Capability profiles instead of a simulation heart

Convenient complete engines should be assembled through plugin groups:

```text
PlatformerCorePlugins
ActionPlatformerPlugins
AdventurePlatformerPlugins
PlatformFighterPlugins
AmbitionGamePlugins
```

A profile selects and configures capabilities. It does not become their implementation owner.

This is comparable to Unity feature sets and Bevy plugin groups: developers get convenient batteries-included compositions without requiring every capability to live in one package. ([Unity Documentation][4])

For example:

```text
PlatformFighterPlugins
├── PlatformerCorePlugins
├── CombatPlugins
├── KnockbackPlugins
├── LedgePlugins
├── MatchPlugins
├── StockRulesPlugin
├── FighterHudReadModelPlugin
└── platform-fighter integration adapters
```

The Smash demo would then pressure-test a reusable profile rather than add more branches to the global actor crate.

## 5. Providers remain product owners

Providers should continue to own:

* named characters;
* worlds and stages;
* movesets;
* roster policy;
* dialogue;
* assets;
* match presets;
* product-specific rules;
* presentation identity.

A provider selects capability profiles and contributes content to them. It should not need to edit engine crates.

## 6. Authoring and presentation remain parallel consumers

Authoring tools should produce schemas and prepared content consumed by capabilities.

Presentation should consume stable read models and effects.

Neither should pass through an actor monolith merely because the thing being authored or rendered happens to be attached to an actor.

# The missing “growth law”

The repository needs an architectural rule that answers:

> How does the next feature enter?

I would make this the governing decision tree:

1. **Does it introduce a reusable state machine or behavior?**
   It belongs to a domain capability and its plugin.

2. **Does it connect two existing capabilities?**
   It belongs to a narrow integration plugin or an opinionated profile.

3. **Is it named game content or product policy?**
   It belongs to a provider.

4. **Is it visual, audible, or observer-relative?**
   It belongs to presentation over a read-model/effect seam.

5. **Is it import, generation, validation, or editing?**
   It belongs to authoring tooling and schemas.

6. **Does it require changing the actor protocol itself?**
   Only then should it modify the small actor-core contract.

7. **Can it only be implemented by editing a giant integration crate?**
   That is evidence of a missing extension seam. Add the seam as part of the feature.

That last rule is what prevents the next monolith.

Without it, any extracted `ambition_actor_runtime` will simply become the new destination for every cross-domain feature.

# What `ambition_actors` should become

I would not begin by carving it into a predetermined crate list.

First establish the target model. Then let `ambition_actors` dissolve in two directions.

### The durable actor kernel

The genuinely universal body/control/lifecycle protocol becomes a small focused crate or a clearly isolated part of existing primitives.

### The integration profile

The residual “everything needed for Ambition-style platformer gameplay” can temporarily become something honestly named like:

```text
ambition_action_platformer
```

or:

```text
ambition_platformer_gameplay
```

But its role must be composition:

* install domain plugins;
* install narrow adapters;
* establish ordering;
* supply opinionated defaults.

It must progressively stop owning leaf systems.

That is different from merely renaming the current monolith. The test is whether a new capability is implemented below it and only selected by it.

# How to get there without spending weeks on another blind refactor

Before moving substantial code, write one new architectural document:

## “Capability composition and engine growth doctrine”

It should define:

* actor protocol versus actor capabilities;
* domain plugin completeness;
* integration-plugin ownership;
* profile/plugin-group responsibilities;
* provider responsibilities;
* schedule and rollback participation;
* dependency direction;
* the new-feature decision tree;
* executable dependency predicates.

Then pressure-test that architecture with three very different additions:

1. **Smash stocks, percent, and respawning**
   This tests match rules, body lifecycle, combat integration, and a platform-fighter profile.

2. **A noncombat dialogue-driven actor/provider**
   This tests whether “actor” has accidentally remained combat-shaped.

3. **A new independently usable movement capability**
   This tests whether a consumer can add mechanics without pulling in menu, persistence, audio, bosses, or the complete Ambition sandbox.

Implement these without allowing them to disappear into `ambition_actors`. Where that proves impossible, identify the missing protocol and create it.

Only then begin moving existing modules behind the proven seams.

## Executable proofs should include

* a movement-only headless consumer;
* a combat platformer consumer;
* a platform-fighter consumer;
* a noncombat provider;
* the complete Ambition game;
* dependency checks ensuring domain crates do not reach upward;
* confirmation that a minimal consumer does not link unrelated capabilities.

This is much more valuable than choosing a target LOC for `ambition_actors`.

# Prototype Ambition 1.0 API

## 1. Grounded diagnosis

The current `ambition` crate is called a facade, but `crates/ambition/src/lib.rs` directly reexports approximately 39 implementation crates.

The external Outlander fixture depends only on `ambition` and Bevy, which is good, but its implementation reaches through:

* 18 top-level `ambition::...` modules;
* approximately 47 distinct deeper API paths;
* actor internals;
* runtime preparation types;
* shell composition;
* asset-source setup;
* catalog fragments;
* sheet registration;
* roster registration;
* rollback codecs;
* simulation schedule internals.

The visible demo shells must currently understand the ordering among:

* Bevy foundation plugins;
* asset source registration;
* engine plugins;
* host plugins;
* shell composition;
* provider registration;
* asset catalog construction;
* presentation;
* audio.

Character authoring is spread across at least four surfaces:

1. `CharacterCatalogFragment`;
2. `register_character_sheet_ron`;
3. `CharacterDefinition`;
4. `CharacterRosterFragment` or spawn-specific actor data.

A provider must currently understand `PlatformerExperienceAuthoring`, `AuthoredCatalogFragments`, route IDs, preparation labels, catalog expectation flags, and a system returning `PreparedPlatformerSource`.

That is an engine-integration API. It is not yet a game-author API.

The current pieces contain much of the correct machinery. The public abstraction is simply one level too low.

## 2. The stable 1.0 mental model

A game author should need only these primary concepts:

1. **Platformer app** — the host and simulation configuration.
2. **Experience** — something the app can launch.
3. **Module** — content and scoped rules that can also be embedded in another experience.
4. **Character** — authored identity and capabilities.
5. **Actor archetype** — how a character is controlled and staged in a particular role.
6. **World** — rooms, links, placements, and an entry point.
7. **Rules plugin** — game-owned simulation policy using stable engine phases.
8. **Game harness** — the same experience driven headlessly.

The exact crate tree must not appear in this mental model.

## 3. Application composition

The normal visible executable should look approximately like this:

```rust
use ambition::prelude::*;
use bevy::prelude::*;

fn main() {
    App::new()
        .add_plugins(
            PlatformerApp::windowed()
                .simulation(Simulation::Fixed60)
                .experience(Outlander)
                .start(OUTLANDER),
        )
        .run();
}
```

A headless application should differ only in host policy:

```rust
let mut app = App::new();

app.add_plugins(
    PlatformerApp::headless()
        .simulation(Simulation::Fixed60)
        .experience(Outlander)
        .start(OUTLANDER),
);
```

A rollback application should differ only in simulation policy:

```rust
app.add_plugins(
    PlatformerApp::headless()
        .simulation(Simulation::Rollback { participants: 1 })
        .experience(Outlander)
        .start(OUTLANDER),
);
```

`PlatformerApp` should remain a Bevy plugin or plugin group. This is not a replacement runtime wrapped around Bevy.

It should internally own the currently fragile ordering among:

* asset-source installation;
* Bevy foundation;
* simulation host;
* platformer runtime;
* window/device host;
* shell;
* experience registration;
* asset preparation;
* presentation;
* optional audio.

The ordinary game author should not name:

* `PlatformerEnginePlugins`;
* `PlatformerHostPlugins`;
* `ShellComposition`;
* `PlatformerAssetsPlugin`;
* `add_headless_foundation`;
* `init_engine_states`.

Those remain useful internal assembly units, but they are not the desired 1.0 entry surface.

## 4. Experience API

An experience is a launchable package with an identity, asset roots, entry point, content, rules, and presentation policy.

```rust
pub trait Experience: Send + Sync + 'static {
    fn manifest(&self) -> ExperienceManifest;

    fn build(
        &self,
        game: &mut ExperienceBuilder<'_>,
    ) -> Result<(), ExperienceBuildError>;
}
```

Outlander should look roughly like this:

```rust
pub struct Outlander;

impl Experience for Outlander {
    fn manifest(&self) -> ExperienceManifest {
        ExperienceManifest::new(OUTLANDER, "Outlander")
            .description("A small traversal and combat proof")
            .assets(AssetRoot::crate_relative("assets"))
            .entry(
                EntryPoint::new(OUTLANDER_WORLD, OUTLANDER_RIDGE)
                    .controlled_character(WANDERER),
            )
            .audio(AudioPolicy::Silent)
            .presentation(PresentationProfile::default_platformer())
    }

    fn build(
        &self,
        game: &mut ExperienceBuilder<'_>,
    ) -> Result<(), ExperienceBuildError> {
        game.character(wanderer())?;
        game.archetype(sentry())?;
        game.world(outlander_world())?;

        game.rules(OutlanderRules);
        game.rollback()
            .component::<BeaconCharge>("beacon_charge")?;

        Ok(())
    }
}
```

This removes normal author knowledge of:

* gameplay and launcher route IDs;
* preparation labels;
* `AuthoredCatalogFragments`;
* `expects_music` and similar manually synchronized flags;
* `PreparedPlatformerSource`;
* `RoomSet`;
* `ActiveRoomMetadata`;
* `LdtkRuntimeIndex`;
* `StartingCharacter`.

The engine can derive route and preparation identities from the experience manifest. Audio expectations can be inferred from the content the experience registers.

The prepared source and session builder remain important engine concepts, but they become implementation products of the experience lifecycle rather than things every provider constructs.

## 5. `ExperienceBuilder` must remain federated

`ExperienceBuilder` must not become another giant central API with one method for every possible feature.

It should hold only common context:

```rust
pub struct ExperienceBuilder<'a> {
    app: &'a mut App,
    experience: ExperienceId,
    namespace: ContentNamespace,
    default_mode: ModeId,
}
```

Each domain should implement its own extension trait:

```rust
pub trait CharacterAuthoringExt {
    fn character(
        &mut self,
        character: CharacterSpec,
    ) -> Result<&mut Self, CharacterAuthoringError>;
}

pub trait WorldAuthoringExt {
    fn world(
        &mut self,
        world: WorldSpec,
    ) -> Result<&mut Self, WorldAuthoringError>;
}

pub trait AudioAuthoringExt {
    fn audio(
        &mut self,
        audio: AudioPack,
    ) -> Result<&mut Self, AudioAuthoringError>;
}
```

The facade reexports these traits through `ambition::prelude`.

This is an important anti-monolith property:

> Adding an audio capability extends the experience context from the audio domain. It does not add an audio branch to one universal experience implementation.

The same approach applies to combat, dialogue, encounters, projectiles, items, and later capabilities.

## 6. One character source document

The 1.0 authoring surface should replace the current catalog/definition split with one typed `CharacterSpec`.

```rust
fn wanderer() -> CharacterSpec {
    CharacterSpec::new(WANDERER, "Outlander")
        .visual(
            CharacterVisual::sheet(
                SpriteSheetRef::new("sprites/outlander.png")
                    .manifest("sprites/outlander_spritesheet.ron"),
            )
            .portrait("portraits/outlander.png"),
        )
        .body(
            BodySpec::sprite_authored(1.0)
                .max_health(1)
                .mass(1.0),
        )
        .movement(
            MovementSpec::axis(
                AxisMovement::platformer()
                    .run_speed(140.0)
                    .jump_speed(280.0),
            ),
        )
        .actions(ActionSet::none())
        .voice([
            "The ridge is quieter than it looks.",
            "Something is watching from above.",
        ])
}
```

`CharacterSpec` is authored input, not one live runtime component. Preparation may lower it into separate products:

```text
CharacterSpec
    ├── PreparedCharacterSimulation
    ├── PreparedCharacterPresentation
    ├── PreparedCharacterAudio
    └── PreparedCharacterAuthoringMetadata
```

That preserves the simulation/presentation boundary without forcing authors to distribute one character across unrelated registries.

Both Rust builders and RON files should produce the same `CharacterSpec`. There should not be a code-authored character model and a different file-authored character model.

The current `CharacterDefinition` is close to the beginning of this API, but it must absorb or replace the applicable parts of `CharacterCatalogEntry`.

A public field should either:

* reach a real preparation and runtime consumer; or
* be rejected as unsupported.

The current prepared-but-unconsumed portrait field is exactly what the 1.0 API must prevent.

## 7. Separate character identity from actor role

A brain is not a character identity property. Faction, encounter role, patrol bounds, and respawn policy are not character identity properties either.

Those belong to an actor archetype:

```rust
fn sentry() -> ActorArchetype {
    ActorArchetype::new(SENTRY, SENTRY_CHARACTER)
        .controller(
            BrainSpec::patrol()
                .effort(0.65)
                .notice_radius(220.0),
        )
        .faction(Faction::Hostile)
        .contact_damage(1)
        .respawn(RespawnPolicy::OnRoomReenter)
}
```

This distinction should replace the current conceptual overlap among:

* character catalog rows;
* character definitions;
* hostile roster rows;
* spawn requests;
* default brain bindings.

The durable rule is:

```text
CharacterSpec = what this body identity is and can do
ActorArchetype = how an instance is controlled and staged in this role
Placement = where one instance enters a world
```

A controlled body, CPU body, peaceful NPC, boss participant, and possessed body can all use the same character identity under different bindings.

## 8. World API

The existing `RoomSpec` is already close to a good public type.

A world should add the missing graph and entry abstraction:

```rust
fn outlander_world() -> WorldSpec {
    WorldSpec::new(OUTLANDER_WORLD)
        .entry(OUTLANDER_RIDGE, SpawnPointId::new("start"))
        .room(outlander_ridge())
}
```

A room can author ordinary placements directly:

```rust
fn outlander_ridge() -> RoomSpec {
    RoomSpec::new(OUTLANDER_RIDGE, ridge_geometry())
        .spawn(
            ActorPlacement::new(SENTRY)
                .id(SENTRY_0)
                .at(Vec2::new(420.0, 460.0)),
        )
        .transition(
            TransitionPlacement::new("upper_gate")
                .destination(OUTLANDER_RIDGE, "upper_ledge"),
        )
}
```

Common actor placements should not require a `RoomContentStagingRegistry` closure.

Advanced provider-owned placement kinds may still register a lowering implementation:

```rust
game.placements()
    .register::<BeaconPlacement>(BeaconLowerer)?;
```

But ordinary actors, pickups, doors, encounters, and transitions should use typed common placement records.

LDtk and Rust-authored worlds should both produce the same `WorldSpec` or backend-neutral world IR.

## 9. Embeddable modules

The vision requires Mary-O and Sanic to run both standalone and inside Ambition. That should become a first-class API concept rather than a pair of `hosted()` and `global()` constructors.

```rust
pub trait GameModule: Send + Sync + 'static {
    fn manifest(&self) -> ModuleManifest;

    fn build(
        &self,
        module: &mut ModuleBuilder<'_>,
    ) -> Result<(), ModuleBuildError>;
}
```

Sanic would expose one module:

```rust
pub struct SanicModule;

impl GameModule for SanicModule {
    fn manifest(&self) -> ModuleManifest {
        ModuleManifest::new(SANIC_MODULE)
            .mode(SANIC_MODE)
            .assets(AssetRoot::crate_relative("assets"))
    }

    fn build(&self, module: &mut ModuleBuilder<'_>) -> Result<(), ModuleBuildError> {
        module.character(sanic())?;
        module.world(sanic_speedway())?;
        module.rules(SanicRules);
        Ok(())
    }
}
```

The standalone experience includes it:

```rust
impl Experience for SanicExperience {
    fn build(&self, game: &mut ExperienceBuilder<'_>) -> Result<(), ExperienceBuildError> {
        game.include(SanicModule)?;
        Ok(())
    }
}
```

Ambition includes the same module:

```rust
game.include(SanicModule)?;
game.include(MaryOModule)?;
```

The rules always use their mode scope. There is no separate global implementation:

```rust
app.add_sim_systems(
    SimPhase::Consequences,
    sanic_rules.run_if(active_mode(SANIC_MODE)),
);
```

In the standalone world, every Sanic room carries `SANIC_MODE`. Inside Ambition, only the mounted Sanic rooms do.

That makes standalone versus embedded composition a property of the world and host, not a constructor flag inside every rules plugin.

## 10. Stable simulation extension API

Game-owned systems should not need to know `SimScheduleExt`, `SandboxSet`, or which Bevy schedule GGRS happens to drive.

The public API should provide:

```rust
app.add_sim_systems(SimPhase::Consequences, charge_beacon);
```

Internally this chooses the configured simulation schedule and the appropriate ordered set.

The schedule vocabulary should be hierarchical.

A small stable coarse vocabulary might be:

```rust
pub enum SimPhase {
    Prepare,
    Control,
    Integrate,
    Consequences,
    Lifecycle,
    Observe,
}
```

Domains expose narrower phases when necessary:

```rust
CombatPhase::{
    Trigger,
    Playback,
    Materialize,
    Resolve,
    Settle,
}

CharacterPhase::{
    Project,
    ResolvePersona,
    GateControl,
}

RoomPhase::{
    Detect,
    Commit,
    Rebuild,
}
```

This is already latent in:

* `PlatformerRuntimeSet`;
* `PlayerInputSet`;
* `WorldPrepSet`;
* `CombatSet`;
* `RoomTransitionSet`;
* `PlayerSimulationSet`.

The 1.0 API should promote the semantic phases and retire the `SandboxSet` name from ordinary game code.

## 11. Game-owned authoritative state and rollback

The existing domain-owned rollback registration is a strong foundation, but the authoring burden should become smaller.

A game-owned component should look like this:

```rust
#[derive(Component, Clone, Debug, Default, Snapshot)]
pub struct BeaconCharge {
    pub seconds: f32,
    pub ticks: u32,
}
```

Registration should inherit the experience namespace:

```rust
game.rollback()
    .component::<BeaconCharge>("beacon_charge")?;
```

The author should not repeat an owner string.

A derive macro should generate canonical codecs for supported fields and reject unsupported fields at compile time. Explicit custom codecs remain available for unusual state.

Rollback registration remains explicit because it is part of the compatibility schema.

## 12. Engine-owned contracts are installed by their owners

Current Mary-O and Sanic rules plugins manually call `add_message` or `init_resource` for numerous engine-owned types so that narrow tests do not panic.

That should not be part of normal game code.

The rule should be:

> Installing a capability installs its complete public contract.

For example:

* combat installs hit messages;
* room lifecycle installs replay requests;
* VFX installs VFX messages;
* audio installs SFX messages;
* actor lifecycle installs death and restart facts.

A rules plugin initializes only state it owns.

Focused tests should use a capability-aware test app:

```rust
let mut app = SimTestApp::new()
    .with_capability(Combat)
    .with_capability(RoomLifecycle)
    .build();
```

Game code should not repeat engine initialization to compensate for incomplete plugin ownership.

## 13. Headless and test API

The current `SandboxSim` is a useful starting point, but a game agent should not provide a custom composition closure after already defining an experience.

```rust
let mut game = GameHarness::new(Outlander)
    .simulation(Simulation::Fixed60)
    .build()?;

game.activate()?;

game.step_for(
    180,
    Controls::default().move_x(1.0),
);

assert_eq!(game.active_room(), OUTLANDER_RIDGE);
```

The same experience should run under sync-test rollback:

```rust
let mut game = GameHarness::new(Outlander)
    .simulation(Simulation::RollbackSyncTest {
        participants: 1,
        check_distance: 4,
    })
    .build()?;
```

The harness should own:

* activation;
* settling the activation boundary;
* starting rollback from the valid live baseline;
* control-frame routing;
* observations;
* structured preparation failures;
* deterministic dumps.

A game should not have to know that rollback must begin eight updates after activation because construction commands have settled.

## 14. Public module layout

The 1.0 facade should be organized by concepts, not internal crates:

```text
ambition::app
ambition::experience
ambition::character
ambition::actor
ambition::world
ambition::combat
ambition::sim
ambition::lifecycle
ambition::effects
ambition::view
ambition::test
ambition::prelude
```

Normal game code should not import:

```text
ambition::actors
ambition::runtime
ambition::host
ambition::game_shell
ambition::platformer
ambition::load
```

Those names expose the current implementation topology.

The underlying crates can remain independently usable for engine developers, but the 1.0 compatibility promise should be made at the role-based `ambition` surface.

The current umbrella is a namespace mirror. The target facade is a semantic API.

## 15. Why this does not create another monolith

There are three safeguards.

### The facade owns no behavior

It reexports public contracts and provides assembly contexts. Character behavior remains in the character domain, world behavior in the world domain, combat behavior in combat, and so on.

### Domain extension traits grow the API

A new capability extends `ExperienceBuilder` through its own trait. It does not add another branch to a central provider switch.

### Capabilities are plugins; profiles compose them

Reusable capability groups remain ordinary Bevy plugins:

```rust
game.capability(ActionPlatformerCapabilities);
game.capability(PlatformFighterCapabilities);
```

Named policy remains a game rules plugin:

```rust
game.rules(SmashStockRules);
```

The profile selects capabilities. It does not implement them.

## 17. API acceptance tests

The prototype should not be judged by whether the wrappers compile. It should be judged by consumer experience.

### Outlander

* Visible `main.rs` is approximately 10 lines.
* No route IDs.
* No prepared runtime types.
* No engine asset root.
* No raw catalog fragment.
* No `ambition::actors` imports.
* Custom authoritative rollback state requires one derive and one registration.

### Mary-O

* One character specification.
* One world specification.
* Rules contain game policy, not engine message initialization.
* The same module works standalone and embedded.
* Programmatic rooms still use the canonical world IR.

### Sanic

* The movement identity is authored through the character API.
* The same rules plugin works standalone and embedded.
* Loop and momentum behavior require no actor-monolith imports.
* HUD publication uses one stable readout API.

### Smash

* Platform-fighter capabilities are installed as a reusable capability group.
* Match rules remain provider-owned.
* Multiple characters retain distinct movement identities.
* Match activation and rollback use public lifecycle seams.
* Stocks, percent, respawn, DI, and stage rules do not add branches to a universal actor API.

### Architecture policy

Game crates should be mechanically forbidden from importing the internal-shaped facade modules listed above.

## 18. Prototype sequence

This should precede a major `ambition_actors` split.

### Phase 1 — write the call sites first

Add a short `docs/sdk/api-prototype.md` containing:

* a minimal visible game;
* an experience;
* one character;
* one actor archetype;
* one world;
* one rules system;
* one rollback component;
* one headless test.

Do not implement until the call sites read like a library someone would choose.

### Phase 2 — implement the facade over current machinery

Implement:

* `PlatformerApp`;
* `Experience`;
* `ExperienceManifest`;
* `ExperienceBuilder`;
* role-based facade modules;
* the first character/world/rollback extension traits.

This can delegate to the current catalogs, provider lifecycle, engine groups, and session builder. No repository move is required.

This is not a compatibility shim. It becomes the canonical public surface immediately.

### Phase 3 — migrate Outlander

Outlander is the best first consumer because its explicit purpose is to expose SDK leaks.

Delete every raw internal path that the prototype makes unnecessary.

Revise the API when Outlander still needs something structurally unreasonable.

### Phase 4 — migrate Mary-O and Sanic

These pressure-test:

* larger rule sets;
* HUDs;
* audio;
* multiple rooms;
* authored movement identity;
* standalone versus embedded composition.

Do not keep old and new provider paths in parallel. Migrate and delete.

### Phase 5 — pressure-test with Smash

Smash determines whether the API supports:

* participant topology;
* character selection;
* match construction;
* platform-fighter capabilities;
* rollback;
* mode-owned rules;
* stock lifecycles.

Only after these consumers should the stable 1.0 subset be declared.

### Phase 6 — reorganize internals behind the API

Once the call sites are stable, `ambition_actors` can be decomposed according to the capabilities the API has proven.

The later repository or submodule move then changes package location, not game code.

## Conclusion

The public 1.0 boundary should be designed before another large internal refactor.

The persistent architecture should be:

```text
PlatformerApp
    hosts Experiences

Experience
    composes Modules, content, capabilities, rules, and presentation

domain-owned extension traits
    register Characters, Worlds, Audio, Combat, Dialogue, etc.

stable simulation phases and lifecycle facts
    let ordinary Bevy plugins extend behavior

GameHarness
    drives the exact same Experience headlessly
```

The essential product test is:

> Can a game agent implement a character, room, mechanic, or complete demo while thinking in terms of characters, worlds, rules, lifecycle, and observations—without learning the current crate topology?

Today the answer is no. The engine has many of the necessary seams, but authors must still understand how the engine is assembled.

This prototype API would turn those seams into a coherent product surface, while allowing the internal crates—including `ambition_actors`—to continue evolving underneath it through 1.0 and beyond.
