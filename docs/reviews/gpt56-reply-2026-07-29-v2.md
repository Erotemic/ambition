### Rollback ownership belongs in the capability model immediately

Claude is correct that this is not a later cleanup.

A federated public API over a central private rollback type list would reproduce the next monolith before the first one is dismantled. The recent omission of `ActiveMatch`, `MatchSeat`, `MatchTeam`, and `RulesetOwnsDeath` is concrete evidence that registration living away from the owning domains creates recurring defects. 

The important distinction is:

> A centralized assembled rollback registry is fine. Centralized ownership of its entries is not.

Each domain plugin should contribute a fragment:

```rust
pub struct RollbackSchemaFragment {
    pub owner: CapabilityId,
    pub components: Vec<RollbackComponentRegistration>,
    pub resources: Vec<RollbackResourceRegistration>,
}
```

The runtime should:

1. gather fragments during composition;
2. detect duplicate stable names;
3. validate codecs and supported state;
4. produce one deterministic ordered schema;
5. fingerprint it;
6. freeze it before a rollback session begins.

Thus combat owns combat snapshot entries, match rules own match entries, and an external game owns its entries. The runtime owns only assembly and execution.

> An Ambition capability is a composable unit of authoring, behavior, lifecycle, deterministic state, schedule participation, and observation.

That means installing a combat capability should install together:

* its public vocabulary;
* its authoring/preparation surface;
* its systems;
* its stable simulation phases;
* its rollback schema contribution;
* its lifecycle handling;
* its diagnostics and read models;
* its headless test support.

## Where I would refine Claude’s open questions

### `Experience` and `GameModule` should not both be behavioral traits

Claude is right that two similar traits are too much conceptual overhead.

I would use:

```rust
pub trait GameModule {
    fn build(
        &self,
        game: &mut GameBuilder<'_>,
    ) -> Result<(), GameBuildError>;
}
```

and make an experience a declarative root value:

```rust
pub struct ExperienceSpec {
    pub id: ExperienceId,
    pub title: String,
    pub entry: EntryPoint,
    pub modules: Vec<Box<dyn GameModule>>,
    pub presentation: PresentationProfile,
    pub asset_roots: Vec<AssetRoot>,
}
```

This yields one implementation concept and one launch concept:

* **Game module:** reusable content, capabilities, and rules.
* **Experience:** a launchable arrangement of modules with an entry point and host-facing metadata.

Sanic implements one `GameModule`. Its standalone game wraps that module in an `ExperienceSpec`. Ambition embeds the same module into its larger experience.

That is clearer than either two parallel traits or one trait with an optional entry point.

### `ActorArchetype` is too broad to stabilize yet

Claude’s concern is valid. Controller policy, faction, contact damage, and respawn policy do not share one lifecycle.

The first API prototype should probably avoid elevating `ActorArchetype` into a central 1.0 noun.

A safer initial model is:

```text
CharacterSpec
    intrinsic identity and capabilities

ControllerSpec
    human, CPU, replay, remote, provider

ActorPlacement
    character + controller + local placement overlays

Mode/room/match rules
    respawn and other scope-owned policies
```

Reusable actor templates can be added as convenience compositions after Mary-O, Sanic, Outlander, and Smash demonstrate a stable repeated shape.

In particular, respawn policy should remain owned by the scope that gives it meaning:

* room lifecycle in an adventure game;
* stock rules in a platform fighter;
* checkpoint policy in another mode.

### Rollback should not be presented as a trivial simulation enum arm

Claude is right that this API:

```rust
Simulation::Fixed60
Simulation::Rollback { participants: 1 }
```

makes two radically different lifecycle promises look equivalent.

Rollback is not merely another clock. It is a session-execution policy requiring:

* a frozen schema;
* a complete authoritative baseline;
* stable participants;
* deterministic activation;
* lifecycle rebasing rules;
* confirmation boundaries;
* restoration and observation semantics.

I would separate them:

```rust
PlatformerApp::new()
    .fixed_step(FixedStep::hz(60))
    .session(SessionMode::Local)
```

and eventually:

```rust
PlatformerApp::new()
    .fixed_step(FixedStep::hz(60))
    .session(SessionMode::Rollback(
        RollbackSessionConfig::new(participants),
    ))
```

The rollback variant should not become public until a dedicated acceptance slice proves that its activation contract is honest.
